# Textos e idiomas

Todo texto visível de um app do Prumo mora em arquivos de mensagens, em todos os idiomas do produto, e é lido por um tradutor tipado. Este guia mostra como organizar os textos, usar plural e formatação, trocar de idioma e acrescentar um idioma novo.

O i18n vem do `defineI18n` do `@matizze/prumo-core`, sobre o i18next com ICU. A referência completa está em [core › i18n](../reference/core.md#i18n).

## Onde os textos moram

```text
src/messages/
  pt-BR/
    index.ts          registra os namespaces do idioma
    home.json         os textos da tela home
    clientes.json     os textos da tela clientes
  en/
    index.ts
    home.json
    clientes.json
```

Cada tela tem um JSON por idioma, com o nome da tela. O `index.ts` de cada idioma importa os JSONs e os registra como **namespaces**, com o nome em camelCase:

```ts
// src/messages/pt-BR/index.ts
import clientes from './clientes.json'
import home from './home.json'
import pedidosRecentes from './pedidos-recentes.json'

export default {
  clientes,
  home,
  pedidosRecentes,
}
```

O `make:page` cria os JSONs e faz o registro em todos os idiomas. Para textos que não são de uma tela (os erros, o menu), crie o JSON e registre-o à mão nos dois idiomas; o `prumo check` acusa o JSON sem registro e o registro sem JSON.

## Ler um texto

No model, o `useTranslations` recebe o namespace e devolve o tradutor `t`:

```ts
const t = useTranslations('clientes')

t('title')             // "Clientes"
t('form.name.label')   // chaves aninhadas, com ponto
```

**As chaves são tipadas** pelas mensagens do idioma padrão (`pt-BR`): um namespace ou uma chave que não existe é erro de compilação. Sem namespace, o `t` aceita o caminho completo (`t('clientes.title')`).

O tradutor fica no model, e a view recebe os textos prontos. Assim a view não depende do i18n e pode ser testada ou trocada sozinha.

## Plural, gênero e variáveis (ICU)

As mensagens usam a sintaxe ICU, então a regra de plural de cada idioma fica no texto, não no código:

```json
// src/messages/pt-BR/clientes.json
{
  "greeting": "Olá, {name}!",
  "count": "{count, plural, =0 {Nenhum cliente} one {# cliente} other {# clientes}}",
  "status": "{status, select, active {Ativo} inactive {Inativo} other {Desconhecido}}",
  "since": "Cliente desde {date, date, long}"
}
```

```ts
t('greeting', { name: 'Ana' })        // "Olá, Ana!"
t('count', { count: 3 })              // "3 clientes"
t('status', { status: 'active' })     // "Ativo"
t('since', { date: new Date() })      // "Cliente desde 22 de novembro de 2026"
```

O `prumo check` compara os argumentos de cada mensagem entre os idiomas: se a versão em português usa `{count}` e a inglesa não, ou se um ICU não fecha, ele acusa.

## Números, moedas e datas

O kit do `defineI18n` tem formatadores no idioma ativo. O `src/i18n.ts` gerado exporta só o `I18nProvider` e o `useTranslations`; exporte também o que for usar:

```ts
// src/i18n.ts
export const { I18nProvider, useTranslations, useFormat, useLocale, useChangeLocale, languages, i18n } =
  defineI18n({
    // ...
  })
```

```ts
const format = useFormat()

format.number(1234.5)                 // "1.234,5"
format.compact(12_400)                // "12 mil"
format.percent(0.253)                 // "25,3%" (o valor é uma fração)
format.currency(99.9)                 // "R$ 99,90" (a moeda padrão é BRL)
format.currency(99.9, 'USD')          // "US$ 99,90"
format.date('2026-11-22')             // "22 de nov. de 2026" (o dia escrito, no fuso local)
format.date('2026-11-22T12:00:00Z')   // "22 de nov. de 2026" (texto com hora é um instante)
format.dateTime(new Date())           // "22 de nov. de 2026, 14:30"
format.time(new Date())               // "14:30"
format.relative(Date.now() - 3_600_000) // "há 1 hora"
```

Um texto só com a data (`AAAA-MM-DD`, como a API manda uma data de vencimento) é lido como **data local**: `'2026-11-22'` é dia 22 em qualquer fuso, e não vira dia 21 no Brasil (o `Date` leria meia-noite em UTC). Texto com hora (`2026-11-22T12:00:00Z`), `Date` e número são um instante, formatado no fuso local. Para somar dias ou contar a diferença entre datas `AAAA-MM-DD` na regra de negócio, use `addDays` e `daysBetween` de `@matizze/prumo-core/date`.

O `useFormat` re-renderiza quando o idioma muda. Para outra moeda padrão, passe `defaultCurrency` ao `defineI18n`.

## Trocar de idioma

```ts
// model de um seletor de idioma
const locale = useLocale()              // 'pt-BR' | 'en'
const changeLocale = useChangeLocale()

return {
  locale,
  languages,                            // [{ id: 'pt-BR', name: 'Português (Brasil)', shortName: 'PT', dir: 'ltr' }, ...]
  onChangeLocale: (id: (typeof languages)[number]['id']) => void changeLocale(id),
}
```

Ao trocar, o i18next grava a escolha no `localStorage` (chave `locale`), e o `<html lang>` e o `<html dir>` acompanham. Na próxima visita, o idioma vem do `localStorage`; na primeira, do navegador, aproximado para um idioma do produto (`pt` e `pt-PT` viram `pt-BR`; `en-US` vira `en`). Sem equivalente, vale o idioma padrão.

## Mensagens de validação

As mensagens de erro de um schema zod podem ser chaves de texto:

```ts
export const clienteInputSchema = z.object({
  name: z.string().min(1, 'validation.required'),
  email: z.email('validation.email'),
})
```

Crie um namespace `validation` com os textos nos dois idiomas e, no model, use o `useFieldError` (exporte-o do `src/i18n.ts`). Ele troca a chave pelo texto no idioma ativo, e deixa passar sem mudança o que não é chave:

```ts
const fieldError = useFieldError()

fieldError({ message: 'validation.required' }) // { message: 'Campo obrigatório.' }
fieldError(undefined)                          // undefined
```

## Textos fora de componentes

Para traduzir fora de um componente (num utilitário, na configuração do `QueryClient`), use as versões `get*` do kit, que leem o idioma ativo no momento da chamada:

```ts
const t = getTranslations('errors')
const format = getFormat()
const locale = getLocale()
```

## Acrescentar um idioma

Para acrescentar o espanhol:

1. Crie `src/messages/es/` com um `index.ts` e um JSON por namespace, com as mesmas chaves do português.
2. Registre o idioma no `src/i18n.ts`:

   ```ts
   import es from './messages/es'

   defineI18n({
     messages: { 'pt-BR': ptBR, en, es },
     defaultLocale: 'pt-BR',
     languages: {
       'pt-BR': { name: 'Português (Brasil)', shortName: 'PT' },
       en: { name: 'English', shortName: 'EN' },
       es: { name: 'Español', shortName: 'ES' },
     },
   })
   ```

3. A partir daí, o `make:page` cria o JSON da tela nova também em `es`, com o texto em inglês para você traduzir (um idioma é uma pasta de `src/messages` com `index.ts`).

Para idiomas escritos da direita para a esquerda, passe `rtlLocales: ['ar']` ao `defineI18n`.

> **Limitação conhecida:** o `prumo check` da CLI compara os idiomas `pt-BR` e `en`, e ainda não tem um arquivo de configuração para outros. Para cobrar um idioma a mais, chame a análise num teste do app, com os idiomas do produto:
>
> ```ts
> // src/messages/messages.test.ts
> import { check } from '@matizze/prumo-rules/check'
> import { expect, it } from 'vitest'
>
> it('os textos estão completos em todos os idiomas', () => {
>   const violations = check({ root: process.cwd(), locales: ['pt-BR', 'en', 'es'] })
>   expect(violations.filter((violation) => violation.rule === 'messages')).toEqual([])
> })
> ```

## Mudar o idioma padrão

O idioma padrão (`defaultLocale`) é o de partida quando a detecção não acha nada e o que define os tipos das chaves. Para trocá-lo, mude o `defaultLocale` no `src/i18n.ts`. O `prumo check` usa o primeiro idioma de `locales` como referência das comparações, `pt-BR` na CLI.
